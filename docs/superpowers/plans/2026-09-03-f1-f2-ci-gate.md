# F1+F2 CI Test Gate Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make `./mvnw clean verify` (no `-DskipTests`) actually pass for every one of the 9 Java microservices, then wire a PR-triggered CI workflow that runs it — closing the gap that let a real boot bug (trip-service's `circuitBreakers` readiness crash, F2) reach `main` undetected.

**Architecture:** Standardize every service's `@SpringBootTest` context-load test onto the pattern already proven by `booking-service`/`trip-service`/`payment-service`: disable Spring Cloud GCP's Firestore/Storage auto-config and `@MockBean` every repository the service declares, so the test needs zero real infrastructure or credentials. Then add one new workflow, `.github/workflows/backend-ci.yml`, matrixed over all 9 services, supplying dummy (but valid-shaped) secrets/URLs per service.

**Tech Stack:** Spring Boot 3.2.4 / Java 17, JUnit 5 + Mockito (`@MockBean`), GitHub Actions.

## Global Constraints

- **F2's real fix is a 2-line property change, not a dependency change** — verified empirically: `resilience4j-spring-boot3:2.1.0` is already present in `trip-service` transitively via `spring-cloud-starter-circuitbreaker-resilience4j`. Do not add any dependency to `trip-service/pom.xml`.
- **A2 fail-fast pattern:** every dummy secret used anywhere in this plan (`JWT_SECRET`, `QUOTE_TOKEN_SECRET`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`) must be ≥32 bytes, since each service's own `@PostConstruct` checks reject anything shorter. Use the exact literals given per task — they're already sized correctly, don't shorten them.
- **Never add an in-source default** to any `@Value`, `@FeignClient` URL, or property to make a test pass locally or in CI. All dummy values live only in test-scoped Spring config (`@SpringBootTest(properties = {...})`) or the CI workflow's `env:` block.
- **`backend-deploy.yml` is not touched by any task in this plan.**
- Three services (`package-service`, `media-service`, `notification-service`) currently pass their context-load test **locally on a dev machine that has real Google Application Default Credentials configured** — confirmed by running them: each test log shows `DefaultCredentialsProvider` picking up real ambient credentials. This is not reproducible in a clean CI runner (no ADC, no service account key) and cannot be relied on — the fix in this plan (disabling GCP auto-config, mocking repos) makes each test's success independent of whatever credentials happen to be sitting on the machine that runs it. Don't skip a task because "it already passes" — it passes for the wrong reason.

### Task 7: backend-ci.yml workflow

**Files:**
- Create: `.github/workflows/backend-ci.yml`

**Interfaces:**
- Consumes: every task above — this workflow only succeeds if Tasks 1-6 all landed correctly, since it runs the exact tests those tasks fixed.

`reactive-booking-function` already passes its existing tests today with zero required env vars (verified — it uses `application.yml`, no `${VAR}` placeholders with no default, and its `@SpringBootTest` already tolerates missing RabbitMQ/Redis at context-load time). It needs no test-file changes, just inclusion in this matrix.

- [ ] **Step 1: Write the workflow**

`.github/workflows/backend-ci.yml`:

```yaml
name: Backend CI

on:
  pull_request:
    paths:
      - 'microservices/**'
  push:
    branches: [main]
    paths:
      - 'microservices/**'

jobs:
  test:
    strategy:
      fail-fast: false
      matrix:
        service:
          - identity-service
          - package-service
          - booking-service
          - media-service
          - notification-service
          - trip-service
          - payment-service
          - api-gateway
          - reactive-booking-function
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Set up JDK 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
          cache: maven

      - name: Build shared modules (common-models, platform-security)
        run: |
          if [ -f "microservices/${{ matrix.service }}/pom.xml" ]; then
            cd microservices/common-models && ./mvnw -q clean install
            cd ../platform-security && ./mvnw -q clean install
          fi

      - name: Test ${{ matrix.service }}
        env:
          JWT_SECRET: "test-jwt-secret-0123456789abcdef0123456789abcdef"
          QUOTE_TOKEN_SECRET: "test-quote-token-secret-0123456789abcdef0123456789abcdef"
          RAZORPAY_KEY_ID: "rzp_test_dummy_key_id"
          RAZORPAY_KEY_SECRET: "test-razorpay-key-secret-0123456789abcdef01"
          RAZORPAY_WEBHOOK_SECRET: "test-razorpay-webhook-secret-0123456789abcd"
          IDENTITY_SERVICE_URL: "http://test-identity"
          PACKAGE_SERVICE_URL: "http://test-package"
          BOOKING_SERVICE_URL: "http://test-booking"
          MEDIA_SERVICE_URL: "http://test-media"
          TRIP_SERVICE_URL: "http://test-trip"
          PAYMENT_SERVICE_URL: "http://test-payment"
          NOTIFICATION_SERVICE_URL: "http://test-notification"
        run: |
          cd microservices/${{ matrix.service }}
          ./mvnw -q clean verify
```

Note: every env var is supplied to every matrix job unconditionally, even though most services only need a subset — this is deliberately simple (no per-service `case` branching needed here, unlike `backend-deploy.yml`'s real-secret scoping) because these are dummy CI-only values with no confidentiality concern, not real secrets. A service that doesn't reference a given `${VAR}` in its `application.properties` simply ignores the unused environment variable.

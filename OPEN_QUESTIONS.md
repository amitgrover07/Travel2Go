## Deployment readiness (GitHub secrets + GCP IAM) — action required before next deploy

`backend-deploy.yml` now references two secrets that must exist in the repo's GitHub Actions secrets before the next push to `main`, or the affected services deploy with placeholder/broken values:
- **`TRIP_SERVICE_URL`**: trip-service's Cloud Run URL. Without this, `api-gateway` falls back to `http://trip-tbd` and cannot route any `/api/trips/**` request — this was missing from the workflow entirely until now, meaning trip-service has never actually been reachable through the deployed gateway.
- **`QUOTE_TOKEN_SECRET`**: a real random secret (32+ bytes), must be the **same value** for both `trip-service` and `payment-service` — they validate the same HMAC-signed tokens. A mismatch between the two silently breaks every `bookLeg` call; omitting it entirely means both fall back to the secret hardcoded in source (public in this repo), which defeats the point of signing.

`trip-service`, `payment-service`, and `booking-service` now deploy with `--no-allow-unauthenticated` plus a `roles/run.invoker` grant to the project's default compute service account (see the "Restrict invoker to internal callers" step) — this closes off the public internet, which removing their `api-gateway` routes alone did not (Cloud Run services are independently publicly addressable by default regardless of what routes to them). **This is a partial mitigation, not true per-service isolation**: every Cloud Run service in this project runs as that same default compute service account, so the grant is effectively "any Cloud Run workload in this project can call these three services," not "only api-gateway/trip-service can." Closing that gap for real requires creating dedicated service accounts per service and assigning them via `--service-account` on deploy — a bigger change (needs confirming the deploying `GCP_CREDENTIALS` principal can create service accounts, and that moving off the default SA doesn't strip IAM roles it currently relies on for Firestore/GCS/Pub-Sub access) that wasn't done here without that confirmation. Also confirm in the GCP console that every service really does run as the default compute SA as assumed — if any already has a custom one, the invoker binding needs updating to match.

`QUOTE_TOKEN_SECRET` and `TRIP_SERVICE_URL` are now scoped in the workflow to only the services that read them (`trip-service`/`payment-service` for the secret, `api-gateway` for the URL) via a per-service `CR_ENV_VARS` build step, rather than sprayed to all nine services in the deploy matrix the way the pre-existing secrets (`JWT_SECRET`, `TWILIO_*`, etc.) still are — that broader sprawl predates this work and wasn't touched, but new secrets shouldn't add to it.

## Security follow-ups (Phase 0, found during build)

- **`TripService.bookLeg` used to trust client-supplied `amountPaise`/`quoteToken` — fixed.** It now ignores request-body price/token entirely and instead reads the `Leg`'s own stored `pricePaise`/`quoteToken` (set when the leg was added), validating them via a `QuoteTokenService` (duplicated into `trip-service`, same pattern as `JwtUtil` — no shared security classes across services) before ever calling `booking-service`. A client can no longer alter the charged amount by tampering with the booking request; if the leg's stored quote token doesn't validate (expired, tampered, or missing), `bookLeg` throws before `booking-service` is called at all. `POST /api/trips/{id}/legs/{legId}/book` no longer takes a request body — `BookLegRequest` was deleted as unused. This closes the "two-layered" gap on the `trip-service` side.
- **`booking-service`'s `POST /api/leg-bookings` itself still has no quote-token validation or trip-ownership check of its own** — it still blindly persists whatever `LegBookingRequest` it receives. The risk is now smaller in practice (its only real caller, `trip-service.bookLeg`, always sends a price/token pair it has already validated) and the endpoint is no longer directly callable from outside the service mesh at all (see "Deployment readiness" above — `--no-allow-unauthenticated` + IAM invoker restriction), but the endpoint still has no defense of its own if reached by another service later. Still logged as open: whether a leg booking should only be marked `CONFIRMED` after `payment-service.charge(...)` succeeds, rather than immediately on request — that ordering question is untouched by this fix.
- **`payment-service`'s `POST /api/payments` (`PaymentController.charge`) had no ownership/ACL check on the caller-supplied `bookingRef` — fixed by removing it from the public gateway and restricting its Cloud Run invoker.** Gateway route `[9]` (`Path=/api/payments/**`) was deleted, and the service now deploys `--no-allow-unauthenticated` (see "Deployment readiness" above) — `payment-service` is no longer reachable from outside the service mesh at either layer. `payment-service` has no `Trip`/`Booking` data of its own, so it cannot resolve `bookingRef` → `ownerUserId` to check ownership directly — adding that would require a new cross-service dependency (`payment-service` calling back into `trip-service`) that isn't justified while nothing calls `charge()` in any real flow yet. When `trip-service` (or a future `billing-service`/refund flow) is wired to call `payment-service.charge(...)` internally, re-evaluate: either keep it internal-only forever, or add the ownership check then, informed by whatever calls it by that point.
- **`trip-service` initially shipped (Task 3) with no per-resource authorization** — any authenticated user could read or mutate any other user's `Trip` by guessing/enumerating a `tripId`. This was found by automated security review and fixed within Phase 0 (commit `67bb60f`): `TripController`/`TripService` now bind `ownerUserId` on trip creation and reject non-owner reads/writes with `AccessDeniedException`. No action needed — noted here as a build-history record, since the fix landed as an unplanned addition to this plan rather than as a numbered task.

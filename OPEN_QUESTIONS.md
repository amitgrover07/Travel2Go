# Open Questions

External contracts and decisions this build stubbed behind an interface rather than guessing. Resolve before the corresponding phase ships to production.

## Payments (Phase 0, `payment-service`)
- **UPI provider**: Razorpay vs. Cashfree not yet chosen; no API keys exist in this repo. `PaymentProvider` is implemented today by `SandboxUpiProvider`, which always returns `SUCCESS` with a synthetic `providerRef`. Swap in a real implementation behind the same interface once a provider + keys are confirmed.
- **Quote-token secret**: `quote.token.secret` currently ships a placeholder default in `application.properties` — now duplicated identically in both `payment-service` (issues + validates) and `trip-service` (validates only, added when `bookLeg` was wired to check it). Both must be set to the *same* real secret via `QUOTE_TOKEN_SECRET` in the deploy workflow before this reaches production traffic that isn't sandboxed — a mismatch between the two would silently break every booking.

## Infrastructure (Phase 0 architecture report, carried forward)
- **Redis / RabbitMQ in production**: `.github/workflows/backend-deploy.yml` injects `SPRING_REDIS_HOST` / `SPRING_RABBITMQ_HOST` from GitHub secrets rather than the docker-compose hostnames, implying managed instances (e.g. Memorystore, CloudAMQP) — the exact provider is not declared anywhere in this repository.
- **`backend/` monolith retirement**: confirmed unreferenced by CI, docker-compose, and the frontend, and deleted in Phase 0 Task 1. If anyone was still hitting it directly (bypassing the gateway), that integration is now broken — watch for reports.

## Security follow-ups (Phase 0, found during build)

- **`TripService.bookLeg` used to trust client-supplied `amountPaise`/`quoteToken` — fixed.** It now ignores request-body price/token entirely and instead reads the `Leg`'s own stored `pricePaise`/`quoteToken` (set when the leg was added), validating them via a `QuoteTokenService` (duplicated into `trip-service`, same pattern as `JwtUtil` — no shared security classes across services) before ever calling `booking-service`. A client can no longer alter the charged amount by tampering with the booking request; if the leg's stored quote token doesn't validate (expired, tampered, or missing), `bookLeg` throws before `booking-service` is called at all. `POST /api/trips/{id}/legs/{legId}/book` no longer takes a request body — `BookLegRequest` was deleted as unused. This closes the "two-layered" gap on the `trip-service` side.
- **`booking-service`'s `POST /api/leg-bookings` itself still has no quote-token validation or trip-ownership check of its own** — it still blindly persists whatever `LegBookingRequest` it receives. The risk is now smaller in practice (its only real caller, `trip-service.bookLeg`, always sends a price/token pair it has already validated), but the endpoint has no defense if reached any other way. It is not reachable through `api-gateway` (route `[3]` only matches `/api/bookings/**`), so the only barrier is network-level isolation between services. Still logged as open: whether a leg booking should only be marked `CONFIRMED` after `payment-service.charge(...)` succeeds, rather than immediately on request — that ordering question is untouched by this fix.
- **`payment-service`'s `POST /api/payments` (`PaymentController.charge`) had no ownership/ACL check on the caller-supplied `bookingRef` — fixed by removing it from the public gateway.** Gateway route `[9]` (`Path=/api/payments/**`) was deleted; `payment-service` is no longer reachable from outside the service mesh at all. `payment-service` has no `Trip`/`Booking` data of its own, so it cannot resolve `bookingRef` → `ownerUserId` to check ownership directly — adding that would require a new cross-service dependency (`payment-service` calling back into `trip-service`) that isn't justified while nothing calls `charge()` in any real flow yet. When `trip-service` (or a future `billing-service`/refund flow) is wired to call `payment-service.charge(...)` internally, re-evaluate: either keep it internal-only forever, or add the ownership check then, informed by whatever calls it by that point.
- **`trip-service` initially shipped (Task 3) with no per-resource authorization** — any authenticated user could read or mutate any other user's `Trip` by guessing/enumerating a `tripId`. This was found by automated security review and fixed within Phase 0 (commit `67bb60f`): `TripController`/`TripService` now bind `ownerUserId` on trip creation and reject non-owner reads/writes with `AccessDeniedException`. No action needed — noted here as a build-history record, since the fix landed as an unplanned addition to this plan rather than as a numbered task.
